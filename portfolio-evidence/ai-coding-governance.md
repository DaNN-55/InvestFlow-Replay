# AI Coding 如何被约束和验收

## 人与 AI 的职责

项目作者负责产品规则、领域语言、数据流、任务拆解、接口取舍、风险边界和最终验收。AI Coding 用于加速局部实现、测试补齐和代码审阅，但不能自行扩大需求、替代业务判断或宣布完成。

## 约束方式

1. **先固定任务边界**：每轮只处理一个可验证切片，明确允许修改的文件和停止条件。
2. **通过 interface 验证行为**：Engine、Backend 和浏览器测试都从调用者可见 interface 断言，不把内部实现细节当成验收标准。
3. **外部行情放在 seam 后面**：TDX cache 与 synthetic fixture 是两个 adapter；Demo 替换 adapter，不复制业务流程。
4. **真实边界才做校验**：用户输入、Engine 响应、网络和文件存储在入口处校验；不靠静默 fallback 掩盖错误。
5. **状态修改可追溯**：订单 action ID、revision、原始盲评、复盘修正和战法版本都保留并发或不可变约束。
6. **完成必须有证据**：局部测试通过后还要运行 Engine、Backend、Web unit、E2E、lint、build，并实际走离线 Demo。

## 验收层次

| 层次 | 主要责任 |
| --- | --- |
| Engine | 行情合同、数据质量、确定性 fixture、缓存与连接 fallback |
| Backend | 会话状态机、订单/成交、幂等与 revision、SQLite 持久化、错误映射 |
| Web unit | 展示转换、状态组合、草稿串行化、图表不偷看未来数据 |
| Browser E2E | 用户可见流程、确认交互、四类状态文案 |
| Offline smoke | Web → Backend → Engine → SQLite 的真实 Fixture 链路 |

## 不作出的声明

- 不宣称 AI 独立完成了产品设计或验证。
- 不把使用 API mock 的浏览器 E2E 描述成完整生产链路测试。
- 不把 synthetic 行情、回测或模拟交易等同于真实收益。
- 不给出无法由提交历史、测试报告或运行证据支持的效率数字。

## 人工验收清单

- 需求与改动范围是否一致；
- 失败原因是否可区分，而不是统一显示内部错误；
- Demo 是否完全隔离个人 `storage`；
- 核心请求/响应能否与代码和测试互相对应；
- 浏览器首屏、关键交互、控制台和移动端是否实际检查；
- 未验证项和已知限制是否明确写出。
